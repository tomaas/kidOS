## B) CLASSIFICATION

### (1) MOVE to UI + DB — 10 vars (env becomes fallback)
`ANTHROPIC_API_KEY`, `STORY_MODEL`, `IMAGE_ENABLED`, `GEMINI_API_KEY`,
`IMAGE_MODEL`, `IMAGE_RESOLUTION`, `TTS_ENABLED`, `TTS_PROVIDER`,
`ELEVENLABS_API_KEY`, `DEFAULT_LANG`.

All are parent-meaningful configuration, all already read at call time (no
import-time freeze problem beyond the `serverEnv` const itself). `IMAGE_MODEL`
half-exists in the UI already (the /parents picker with localStorage) —
this work makes the DB the real home. `DEFAULT_LANG` is near-obsolete (since
phase 3 the wizard passes the UI locale); store it as a DB setting defaulting
to the UI language, env fallback kept.

### (2) STAYS env — 7 vars (true infra)
`DATA_DIR`, `DATABASE_URL`, `PORT`, `NODE_ENV`, `SKIP_ENV_VALIDATION`,
`DEV_ALLOWED_HOSTS`, `TURSO_AUTH_TOKEN` (legacy tripwire). Chicken-and-egg:
you cannot store the DB's own location in the DB; ports/paths are the
operator's contract with Docker.

### (3) TRICKY — 5 vars

**VITE_CHILD_NAME / VITE_APP_NAME / VITE_APP_DESCRIPTION / VITE_STORY_LABEL →
MOVE to DB, becoming runtime data.** Full consumer trace:
- `childName` → `portrait.tsx` (hero identity match — `matchesChildName` in
  `src/lib/bureau/identite.ts`, golden-tested in test:bureau on the PURE
  function, which takes childName as an argument → golden unaffected) and
  portrait display fallback.
- `brandingFor(locale)` → `__root.tsx` head (tab title + description; the root
  loader ALREADY fetches `ui-language` per request — same entry point works).
- `appConfig` (frozen FR branding) → `printable-story.tsx` colophon,
  `dynamic-functions.ts` fallback story title. AMENDED (codex #5): these two
  derive branding from the **STORY's frozen lang**, never the UI locale —
  thread childName + overrides and call `brandingFor(storyLang)` (an English
  story printed under a French UI keeps English branding). This honors the
  existing comment in app.ts:36 instead of regressing it.
- The pure `buildBranding` (`src/lib/i18n/branding.ts`) takes `(locale,
  childName)` — **unchanged**, so test:i18n's branding pins stay byte-green.
The mechanical change: branding stops being a module-level const and becomes
loader data (root loader returns `{locale, branding, childName}`) + a plain
server read for server consumers. VITE_* stay honored as the env FALLBACK
(the server can read `process.env.VITE_CHILD_NAME` at runtime; the Dockerfile
ARGs become optional/legacy). Cost: ~5 files rewired; gain: rename the child
without a Docker rebuild — squarely what the user asked for.

**BLOB_READ_WRITE_TOKEN → STAYS env (recommendation).** It selects the media
BACKEND (local disk vs Vercel Blob) and derives the SSRF allowlist host. It is
a deployment-mode property: on the family box (Docker volume) it is never set;
it only exists on ephemeral-filesystem deploys — exactly the deploys where the
"DB" story is different anyway. Making it parent-editable invites a foot-gun
(flip it → new media goes to a cloud bucket) with zero family value, and the
allowlist derivation (`blobHostFromToken`, golden-pinned in test:media) would
need cache-coherent re-derivation. Keep env; revisit only if a cloud deploy
target returns.

## C) TARGET ARCHITECTURE

### C1. Storage: extend `app_settings` (recommended) — no new table
The key/value table exists (migration already shipped, `ui-language` proves
the pattern), cardinality is ~12 rows, values are strings. A dedicated typed
table buys nothing here and costs a migration. Key naming, kebab-case with a
section prefix, canonical list frozen in one module:

```
text:anthropic-api-key   text:story-model
image:enabled            image:gemini-api-key   image:model   image:resolution
tts:enabled              tts:provider           tts:elevenlabs-api-key
story:default-lang
branding:child-name      branding:app-name
branding:app-description branding:story-label
```
Booleans stored as "true"/"false"; enums normalized on read (the
`normalizeLocale` precedent) — a hand-edited row never errors. AMENDED
(codex #14): DB-row parsing is **invalid-means-fallback**, never
invalid-means-disabled — a garbage bool/enum row falls through to the env
value (then code default), it does not silently force `false`. (env.ts's
historical `bool()` keeps its own semantics for env strings.)

### C2. Settings service: `src/server/app-config.ts` (AMENDED: no cache)
One server-only module, the single choke-point (mirrors media-store's design):

- `getAppConfig(): Promise<AppConfig>` — reads ALL settings rows in one query,
  merges with precedence **DB row present → wins; absent → env value → code
  default**, returns a typed frozen object. **NO cache**: ~14 rows in a local
  SQLite file — a fresh read per logical operation is the safer 80/20 (no
  invalidation race, no stale second process, no `invalidateAppConfig`
  machinery). Measured caching can be added later behind the same signature.
- **Full typed shape defined in Chunk 1** (codex #6): `AppConfig =
  { provider: ProviderConfig; branding: BrandingConfig }` — `ProviderConfig`
  mirrors today's category-1 `serverEnv` fields; `BrandingConfig` carries
  childName + the three override strings. The choke-point is frozen from
  Chunk 1; the branding chunk only adds consumers, never reshapes it.
- **Central writers** (codex #9/#11): `setSetting`/`deleteSetting` helpers in
  the same module — EVERY writer goes through them, including the existing
  `saveUiLocaleFn` (rewired). No writer-side cache duty (no cache), but the
  central-writer rule stands so validation/normalization can't be bypassed.
- **Never throws** (getUiLocaleFn precedent): DB unreachable → env-only
  config + server log. The child never sees a config error.
- **Import-graph rule (CRITICAL for goldens)**: `app-config.ts` must NOT
  statically import `~/server/db` (nor any module re-exporting it) — lazy
  `await import("~/server/db")` inside the read function. Otherwise
  `test:coherence` (which imports dynamic.ts under SKIP_ENV_VALIDATION)
  would pull in the db bootstrap. Pinned by a subprocess test (C9).
  `env.ts` keeps its pure env-fallback role and stays import-safe.

### C3. Consumers: ONE snapshot per logical operation (AMENDED)
Config enters at the **server-function boundary**: each handler in
`functions.ts` / `dynamic-functions.ts` / `settings-functions.ts` takes ONE
immutable `AppConfig` snapshot up front and **threads it down** into gates,
providers and logging as an explicit parameter. Consequences:
- No mixed generations within an operation (codex #4): "image enabled" and
  its key/model/resolution always come from the same snapshot.
- Sync helpers stay sync: `logTextGen()` (dynamic.ts:63) receives the model
  from the threaded snapshot instead of awaiting anything.
- Provider signatures change: `generateBeat`/`generateStoryArc`,
  `generateImage`, `getTtsProvider(config)` gain a config (or sub-config)
  parameter — this is an API-signature refactor, not a mechanical
  find-replace (codex #15).
- `getPublicFlags(config)` derives from the snapshot — toggling IMAGE/TTS in
  the UI applies on the next request, no rebuild.
- **Client consistency boundary = reload** (codex #10): the root route keeps
  `staleTime: Infinity`; the saving tab calls `router.invalidate()`, any
  OTHER tab sees new branding/locale/flags on its next reload. Documented,
  no new revalidation machinery.
`media-store.ts` and `db/index.ts` keep reading `serverEnv` (category 2/3 —
unchanged). `serverEnv` shrinks in ROLE (fallback provider) but keeps its
shape so test:db's env-validation pins change minimally.

### C4. Boot validation: infra-only (AMENDED — codex #1 BLOCKER)
`validateServerEnv()` drops **ALL movable provider/key validation**: the
ANTHROPIC_API_KEY requirement AND the conditional Gemini/ElevenLabs checks
AND the image/TTS gating logic (a key living only in SQLite, or a DB setting
disabling a feature env enables, must never fail boot). Only INFRA validation
remains boot-fatal: DATABASE_URL shape checks (+ DATA_DIR derivation). Key
checks move to point-of-use: story creation without a resolvable key returns
the existing typed soft-failure for the child, AND the settings server fn
returns a deterministic **configuration-status CODE** (codex #12 — distinct
from provider-failure codes) so /parents shows a calm "clé non configurée".
No provider network call is attempted when the key is absent (tested).
`test:db`'s env-validation golden updates accordingly (deliberate,
documented pin change — not a regression).

### C5. Secrets: honest threat model, no theater
Box model: loopback-only, no auth — anyone who can reach the HTTP port IS the
parent; anyone with disk access can read `.env.production` today just as they
could read `app.db` tomorrow. Plaintext in SQLite is therefore an equivalent
posture, stated plainly in README. Rules that DO matter:
- **Never send a secret back to the client.** GET returns
  `{configured: boolean, hint: "sk-ant-…7Yq"}` (last 3-4 chars only).
- **Four clear operations per secret** (AMENDED — codex #2 BLOCKER; under
  DB-wins/env-fallback, "delete row" alone would silently reactivate the env
  key while the UI claims it's erased):
  1. **keep current** — field left empty on save → no write;
  2. **set new value** — upsert the row;
  3. **explicit empty override** — store `""` in the row: masks the env key,
     the feature reads as unconfigured (the honest "Effacer");
  4. **reset to deploy default** — delete the row: env fallback resumes.
  The UI exposes 2/3/4 distinctly ("par défaut (env)" badge shows state 4);
  all four are pinned in `test:settings`.
- Save fns return CODES, never sentences (saveMathSettingsFn precedent).
- Never log values; the existing error paths already keep detail server-side.
- README note: `app.db` backups now contain keys — same care as `.env`.
- No encryption-at-rest: the key would sit next to the DB on the same disk.

### C6. Seed strategy: PURE FALLBACK, no boot copy (recommended)
Do **not** copy env values into the DB at startup. Rationale:
- Zero migration pain either way, but copy-on-boot silently duplicates
  SECRETS into the DB when the operator only consented to .env — surprising,
  and a later .env rotation would be silently ignored (DB copy wins).
- Pure fallback keeps one obvious mental model: "DB row = parent decided in
  the UI; no row = whatever the deploy says". Deleting a row IS "reset to
  deploy default", and the UI can show a "par défaut (env)" badge — the exact
  pattern the image-model picker already uses.
- No write path at boot → test:db's blank-dir boot golden stays clean.

### C7. New /parents settings page — `/parents/reglages` (AMENDED)
Fits the existing card grammar (the 🌍 language card is the model). Sections
as calm cards: **Histoires** (API key, story model), **Images** (toggle, key,
model — absorbing/linking the existing picker —, resolution), **Voix**
(toggle, provider edge/elevenlabs, key). The **Prénom & nom de l'atelier**
section (childName + the three override strings, live derived preview via
the pure `buildBranding`) ships IN THE RUNTIME-BRANDING CHUNK, not before
(codex #7): no mergeable state may present controls that visibly do nothing.
Saves are **field-level patches** executed as ONE SQLite transaction via the
central `setSetting`/`deleteSetting` helpers (codex #11) — two tabs saving
disjoint sections never clobber each other; a failed transaction changes
nothing. All labels in the i18n catalogs (`parents.reglages.*`,
fr/en key parity → test:i18n), templated aria via `formatMessage`. Calm
constraint: parent-only page; no validation nagging — a missing key shows a
neutral "non configurée" state, never red urgency.

### C8. Hot-apply vs restart, per setting (AMENDED: no cache)
- **Hot (next operation)**: all 10 category-1 settings + the 4 branding
  settings — every logical operation takes a fresh snapshot, so a save
  applies to the very next server call. Branding and public flags enter per
  request through the root loader.
- **Restart-required**: none among the moved settings (that's the point).
  Category-2 env stays restart-scoped by nature.
- Client staleness: reload is the documented consistency boundary (C3) — the
  "Écouter" button, image slots and branding reflect changes on the next
  navigation/reload; another open tab converges on its next reload.
  Acceptable and calm.

### C9. Golden-test impact map
- `test:golden` / `test:coherence`: prompt builders are pure — untouched.
  RISK: dynamic.ts's import graph must stay DB-free (C2 rule). Byte-pins safe.
- `test:i18n`: `buildBranding` unchanged; ADD catalog keys in BOTH locales
  (parity check enforces this); calm-wording scan applies to the new labels
  ("clé", "réglages" fine — avoid anything evaluative).
- `test:bureau`: `matchesChildName` pure, takes childName param — unaffected.
- `test:db`: env-validation pins change (C4) — deliberate update in the same
  chunk; boot-on-blank-dir must stay green with NO settings rows.
- `test:media`, `test:routes`, `test:operations`, `test:reading-aids`,
  `test:data-route`: untouched.
- NEW `test:settings` golden (AMENDED — codex #2/#8/#11/#13/#14): precedence
  matrix (db>env>default), the FOUR secret operations (keep / set / empty
  override / reset-to-default), invalid-means-fallback bool/enum parsing
  (missing, true/false, empty override, garbage — each pinned separately),
  masking helper (`hintFor`), never-throw on DB failure, canonical key list
  frozen, field-level patch transactionality (concurrent disjoint updates +
  failed-transaction rollback), PLUS:
  - **Boundary secret-scan**: invoke the read/save server-fn handlers with
    planted secret values and recursively scan the SERIALIZED responses —
    no secret ever crosses the boundary (helper tests alone can't prove it).
  - **Subprocess import-graph test**: a child process imports app-config.ts
    (and dynamic.ts) in a blank tmp dir and asserts NO db file is created;
    plus a static assertion that app-config.ts has no top-level
    `~/server/db` import (direct or via re-export).
  - **No-call-when-unconfigured**: absent key → deterministic config-status
    CODE, zero provider network attempts, calm child wording preserved.

### C10. Dockerfile / compose impact
- Dockerfile: the four `ARG VITE_*` become legacy-optional (kept one release
  for fallback, comment updated). `SKIP_ENV_VALIDATION=1` build unchanged.
- compose.yml: unchanged structurally; `.env.production` may shrink to
  infra-only. `.env.example` rewritten: infra section (stays env) + "everything
  else is set in the UI at /parents/reglages; env values act as defaults".
- README: first-run story becomes "docker compose up → open /parents → paste
  the Anthropic key" — genuinely simpler than today.
